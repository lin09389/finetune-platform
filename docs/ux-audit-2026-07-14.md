## 1. UI / 交互层面缺陷

### 1.1 设计文档三份互相冲突，运行时是第四种

- [`client/DESIGN_SYSTEM.md`](../client/DESIGN_SYSTEM.md) 讲"玻璃拟态 + 8pt 网格 + `.will-animate` / `.gpu-accelerated`"（L5-11、L18-31）
- [`client/MOTION_GUIDELINES.md`](../client/MOTION_GUIDELINES.md) 讲同一套 duration 令牌，但强调"纸质风"外的 spring 曲线（L14-30）
- [`docs/frontend-review-2026-07-08.md#6`](./frontend-review-2026-07-08.md#6-视觉一致性) 已经证实运行时是 Newsreader/Poppins + 纸质风，且 `src/index.css` 是"死代码设计系统"（L152-159）
- 结论：**至少 4 个设计声明并存，前端评审建议以 `variables.css` 为唯一令牌源，本报告支持该决议**

**用户可感知的负面结果**：不同页面字体/圆角/阴影不一致（例如 `Deployment.module.css:9`、`ChatHeader.module.css:5` 硬编码 hex，见前端评审 L155）。

### 1.2 Storybook 形同虚设

`client/src/stories/` 仅有 3 个文件（Button、Header、Page），均是 `npx storybook init` 官方脚手架示例，覆盖 **0 个** 自研组件：

```
client/src/stories/Header.stories.ts       (34 行, 脚手架)

```

但 `client/package.json` 保留了 `storybook` / `build-storybook` / `test-storybook` 完整脚本，`client/storybook-static/` 已构建产物。DESIGN_SYSTEM.md L45 承诺的"`GlassCard`、`NeumorphicButton`、`PremiumInput`"、shared/ 下的 `EmptyState`、`LoadingState`、`PageHeader`、`StatusBadge`、`PageSkeleton`（见前端评审 L57），以及 `AgentTerminalDock`、`Sidebar` 等 **均无 story**。

**建议**：要么最少覆盖 shared/ + 关键 Agent 组件，要么明确移除 Storybook 依赖，避免"有基建但无内容"的假象误导贡献者。

### 1.3 移动端 vs 桌面端差异

仓库根目录截图 `docs/assets/agent-workbench-desktop.png` 与 `docs/assets/agent-workbench-mobile.png` 分别展示了 `/agent` 沉浸式工作台。结合 [`client/src/App.tsx:374`](../client/src/App.tsx#L374)（`isMobile||isTablet` 隐藏侧边栏改抽屉）与 `docs/frontend-review-2026-07-08.md#3` 的评审：

- `/agent` 页面有 **Timeline + ActivityBar + RightDock + TerminalDock** 四栏结构（见 `client/src/agent/components/`），在桌面端由 `AgentResizeHandle` 支持自定义分栏
- 但 `client/src/agent/workbench/` 未见针对 <768px 的响应式布局降级：三栏在小屏上要么被裁切，要么全部渲染导致横向溢出
- 移动端仅在 `MobileNav`（触控 44px 达标）+ 汉堡菜单层级做过适配，Agent 工作台本体未适配

### 2.3 审计日志双写路径 + 上下文全空

**双写路径**：[`server/security/audit_log.py:116`](../server/security/audit_log.py#L116)

```python
self.storage_path = storage_path or Path("data/audit_logs")
```

`Path("data/audit_logs")` 是相对路径，取决于后端进程 cwd：
- `start.bat` 用 `uv run --extra all python -m uvicorn server.main:app` → cwd 为**仓库根** → 写入 `<repo>/data/audit_logs/`
- `start-backend.bat` 回退分支 `cd /d "%~dp0server"` → cwd 为 `server/` → 写入 `<repo>/server/data/audit_logs/`
- 结果：仓库两个位置都有 88 个 `audit_*.jsonl` 文件（见 `data/audit_logs/` 与 `server/data/audit_logs/`），排障时不知看哪个

**上下文全空**：抽样 [`data/audit_logs/audit_2026-07-10.jsonl`](../data/audit_logs/audit_2026-07-10.jsonl) 与 [`server/data/audit_logs/audit_2026-07-03.jsonl`](../server/data/audit_logs/audit_2026-07-03.jsonl)：

```json
{"user_id": null, "session_id": null, "agent_id": null,
 "source_ip": null, "resource_type": null, "resource_id": null,
 "action": "set_api_key",
 "details": {"provider": "mock-preserve-f3fde93b"}, ...}
```

- 所有身份字段均为 `null`
- `details.provider` 是 `mock-preserve-<hash>` 占位数据，说明测试脚本或占位 UI 在真实审计通道里生成噪音
- `server/security/audit_log.py:128-161` 的 `log_event` 支持传 `user_id/session_id/agent_id/source_ip`，但调用方（`api/auth.py` 或 `apps/*`）没有把 `get_current_user()` 上下文传进去

**用户/运维影响**：无法在 UI 或 CLI 回答"谁在什么时候设了哪个 provider 的 key"这一最基础的运维问题。

**建议**：
1. `AuditLogger.__init__` 改为绝对路径（`settings.data_dir / "audit_logs"`）
2. 在 API Key、CUA、Auth 相关路由的调用点补 `user_id=request.state.user_id` 等上下文
3. 剔除 `mock-preserve-*` 类占位数据的写入路径

**建议**：明确"过渡期截止日期"，在 API 层加 deprecation 警告 header（如 `X-Deprecated: use workspace_id since 2026-08-01`），前端错误时明确显示"缺少 workspace"引导。

### 4.1 编码腐化历史事故：TrainingChart

`logs/frontend-dev.err.log:1-16` 记录了明确的 Vite 编译错误：

```
[vite] Internal server error:
client/src/components/TrainingChart.tsx:71:18
Unterminated string constant.
> 71 |     console.log('[TrainingChart] WebSocket 宸茶繛鎺?);
     |                 ^
```

`宸茶繛鎺?` 是标准的 UTF-8 数据被以 GBK 解读后的 mojibake（原文疑为"已连接"）。**闭合单引号丢失**导致 Vite 直接拒绝解析该文件，训练图表页面白屏。

**当前状态**：`grep TrainingChart client/src/**` 已无命中——文件被删除或重命名，事故本身已修复。但 `logs/frontend-dev.err.log` 高达 3638 行 / 365 KB，说明该错误在被修复前被反复触发。

**流程缺口**：
- [`reports/encoding/encoding_scan_report.txt`](../reports/encoding/encoding_scan_report.txt) 声明"问题文件数: 0"，紧接着列出 6 个 `.mdl/.msc` **二进制** ModelScope 元数据文件——扫描工具规则错误
- **真正的源码 mojibake 没被扫描到**
- Windows 中文环境（chcp 936 GBK）下用非 UTF-8 编辑器保存 .tsx 是本项目高风险场景，需要专门的 CI 检查

**建议**：
1. 修 `scripts/check_encoding.py`（如存在），排除二进制扩展，加入源码 mojibake 正则（如 `[\ue000-\uf8ff\u4e00-\u9fff]{2,}` 中出现 `锟|烫|屯|涓|閿` 等 mojibake 高频字）
2. 在 `.github/workflows/ci.yml` 增加编码扫描步骤

## 8. 结论

Finetune Platform 的 UX 现状可以概括为："**主流程能跑，但每个环节都留有历史包袱**"。

- **好的方面**：前端评审已经把最硬核的可访问性、性能、视觉一致性问题梳理得非常细；后端能力分层、能力注册表、GA/Beta/Experimental 边界的设计相当先进；DeepAgents 集成、SSE 流式、检查点恢复等能力都在架构层面有清晰位置
- **系统性缺陷**：DX 层面的启动脚本混乱、审计日志失效、编码扫描漏检、i18n 装饰性摆设、README 幻影脚本，这些都不是难改的技术问题，而是"没人做最后一公里收口"的产物
- **优先级建议**：先啃 P0 的四个（幻影脚本、审计路径、审计上下文、编码扫描规则），再进入前端评审 Phase 1 的可访问性硬伤，同时启动 P1 的启动脚本收敛与 i18n 决策，P2 作为治理性长期任务并行推进

本报告的目的不是罗列所有小毛病，而是把**用户/开发者最易踩坑**的地方分类标注，让下一次 Sprint 规划有据可依。
