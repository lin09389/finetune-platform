 一、我对这个项目的架构理解

  1. 这已经不是一个单纯的“微调平台”

  从实际代码看，你的项目已经演进成一个本地 AI 工作台 / AI 平台壳层，不只是 LoRA/QLoRA 微调工具。

  现在实际覆盖的能力包括：

  - 模型管理
  - 数据集管理
  - 训练调度与状态管理
  - 推理 / 流式聊天
  - RAG / Knowledge Base
  - Memory / Context 注入
  - Agent / Workspace / Task
  - Gateway / Heartbeat
  - CUA / MCP / 文件与项目操作

  核心证据在：
  - server/main.py:368
  - client/src/App.tsx:138

  也就是说，你的产品能力已经明显超过“训练平台 2.0”的初始边界。

  ---
  2. 后端架构：单体 FastAPI，但功能域非常多

  后端是一个大型单体 FastAPI，通过 router 方式拼装多个子系统。

  已经比较成熟的部分

  我认为下面两块是你项目里最像“已形成系统能力”的：

  A. Training 子系统

  这里不是简单的接口拼装，而是有清晰的状态与并发设计：

  - server/core/training_state.py:81
  - server/core/training_queue.py:76
  - server/api/training.py:38

  特点：
  - 线程安全状态管理
  - 队列调度
  - 训练历史
  - 进度推送
  - 任务生命周期比一般 demo 项目完整

  这部分成熟度相对高。

  B. Inference / Chat Context 子系统

  推理侧已经不是简单 /generate，而是有：

  - backend scheduler
  - backend fallback / circuit breaker
  - prompt 安全处理
  - unified context 注入（memory / knowledge / context）

  证据：
  - server/api/inference/routes.py:107
  - server/api/inference/routes.py:189
  - server/api/inference/routes.py:220

  这说明你在“运行时 AI 能力”这条线上，架构方向是对的。

  ---
  3. 前端架构：现代化，但正在经历“功能膨胀”

  前端是 React + TS + Zustand + AntD + Framer Motion，整体组织不差。

  关键点：

  - 应用壳层比较完整
  client/src/App.tsx:173
  - Chat 是目前最复杂的业务中心
  client/src/pages/ChatNew.tsx:202
  - 状态管理已经出现“双中心”现象
    - client/src/store/appStore.ts:14
    - client/src/store/chatStore.ts:15

  也就是说，前端不是不能用，而是已经出现迁移中的重叠状态模型，后续会越来越难维护。

  ---
  4. 当前最大的架构问题：不是“没有功能”，而是“边界失控”

  你现在的主要问题，不是缺少模块，而是：

  架构层面的 4 个风险

  ① 产品边界扩散过快

  一个项目里同时做：

  - Finetune
  - Chat playground
  - Agent platform
  - Workspace
  - Gateway
  - Heartbeat
  - CUA/MCP

  会导致：
  - 代码路径越来越多
  - 真正打通的闭环越来越少
  - UI 看起来很强，但很多路径是半通的

  核心证据：
  - server/main.py:368

  ② 新旧实现并存

  项目里存在明显的“新旧实现叠加”现象，比如：
  - memory old/new
  - knowledge stub/real
  - appStore/chatStore 重叠
  - 某些兼容路由还保留

  这会带来：
  - 同一个功能出现两套入口
  - 开发者容易改错文件
  - 前后端契约容易漂移

  ③ 默认配置有漂移

  比如默认端口就不一致：

  - 后端默认 8001：server/core/config.py:28
  - 前端默认 8000：client/src/services/api.ts:8
  - client/src/App.tsx:194

  这类问题不是“代码报错型 bug”，但会直接影响本地启动体验和认知一致性。

  ④ 一些子系统的 UI 成熟度高于后端真实能力

  尤其是：
  - Knowledge
  - Branching
  - CUA 录制
  - Workspace

  这类地方最容易出现“伪实现”或“乐观 UI”。

  ---
  二、整个项目的功能堵点和伪实现审计

  下面是我按影响程度排的结果。

  ---
  P0 级：关键功能实际不通

  1. Chat Branch Manager 前后端根本不是同一套存储

  结论：这是一个真实的功能断路点。

  问题

  前端 Chat Branch 管理器请求的是：
  - /api/chat/{sessionId}/tree
  - /api/chat/{sessionId}/branches

  但后端 chat_branch.py 使用的是另一套独立文件存储：
  - data/chat/session_{session_id}.json
  - data/chat/branches_{session_id}.json

  而主聊天系统 server/api/chat/session.py 用的是：
  - data/sessions/{session_id}.json

  也就是说：
  主聊天系统写的数据，分支系统根本读不到。

  证据

  - client/src/components/ChatBranchManager.tsx:54
  - client/src/components/ChatBranchManager.tsx:78
  - server/api/chat_branch.py:16
  - server/api/chat_branch.py:62
  - server/api/chat/session.py:105
  - server/api/chat/session.py:176

  影响

  - 用户看不到真实聊天树
  - 分支创建/读取无法基于真实会话工作
  - 这是典型的“UI 有了，后端接口也有了，但底层不通”

  分类

  功能堵点 + 架构断裂

  2. Action Recorder 前端调用了不存在的后端接口

  问题

  - POST /cua/record/save

  但后端实际只有：

  - POST /cua/record/action

  - POST /cua/record/play

  证据

  前端：
  - client/src/pages/ActionRecorder.tsx:153
  - client/src/pages/ActionRecorder.tsx:165
  - client/src/pages/ActionRecorder.tsx:180

  后端：
  - server/api/cua.py:630
  - server/api/cua.py:665
  - server/api/cua.py:683
  - server/api/cua.py:707

  影响

  - 用户无法保存录制动作
  - 无法加载动作文件
  - 无法清空动作集
  - UI 逻辑会给出成功提示，但实际上请求是 404

  分类

  伪实现

  P1 级：高优先级堵点 / 误导性实现

  3. Chat Branch 的“合并分支”是假实现

  问题

  /chat/{session_id}/merge-branch/{branch_id} 这个接口只做了：

  - 检查 branch 是否存在
  - 检查 current_branch_id 是否存在
  - 然后直接返回成功

  它没有真的合并消息、节点、上下文。

  证据

  - server/api/chat_branch.py:173

  关键逻辑本质上就是：
  return {"success": True, "message": "分支已合并"}

  前端却会显示操作成功：
  - client/src/components/ChatBranchManager.tsx:223

  影响

  - 用户会以为分支已合并
  - 实际数据完全没变
  - 这类“成功提示但无副作用”的实现最危险

  分类

  伪实现

  4. Workspace 元数据只存在内存里，服务重启就丢

  问题

  server/api/workspace.py 用的是全局内存字典：

  - workspaces: dict[str, dict[str, Any]] = {}
    - server/api/workspace.py:19

  创建、列表、删除都是围绕这份内存对象。

  虽然文档向量可能写入了 Chroma，但 workspace 元数据本身不持久化。

  证据

  - server/api/workspace.py:19
  - server/api/workspace.py:46
  - server/api/workspace.py:71
  - server/api/workspace.py:143

  前端明显按“可长期存在的工作区”来设计：
  - client/src/pages/WorkspaceManager.tsx:43

  影响

  - 服务一重启，workspace 列表丢失
  - 用户体验上像“系统失忆”
  - 这不是细节 bug，是存储模型没闭环

  分类

  架构堵点

  三、我对这个项目当前状态的判断

  结论一句话

  你的项目不是“没做出来”，而是“做得很大，但真正打通的核心闭环数量还不够”。

  它已经具备以下特征：

  优点

  1. 训练和推理主链路是有真实工程基础的
  2. 前端整体不是 demo 级，已经有平台型 UI 结构
  3. 很多模块不是纯占位，而是有明确的系统设计方向
  4. 你已经在做平台，而不是做单点工具

  问题

  1. 产品边界扩张过快
  2. 新旧实现重叠
  3. 部分功能只有 UI/接口壳，没有真实数据闭环
  4. 有些模块“看起来完成了”，但实际上只完成了 40%-60%

  ---
  四、从架构师角度，我建议你先处理的堵点顺序

  如果按“恢复系统可信度”的优先级，我建议顺序是：

  第一梯队：必须先修

  1. Action Recorder 缺失接口
  2. Chat Branch 存储体系统一
  3. Branch merge 真正实现或先下线按钮
  4. Workspace 元数据持久化

  这四个会直接决定：
  - 用户是否相信系统
  - 功能是否真的能闭环

  ---
  第二梯队：尽快清理

  5. 删掉或明确废弃 server/api/knowledge.py stub
  6. 统一 chat 相关状态源
  7. 统一默认端口和前后端配置源
  8. 梳理哪些 API 是 legacy，哪些是 canonical

  ---
  第三梯队：架构收口

  9. 把项目重新定义成 2~3 条主产品线
  比如只保留：

  - A. Finetune / Training
  - B. Chat / Inference / Knowledge
  - C. Workspace / Agent

  不要让 Gateway / Heartbeat / CUA / MCP 都处于同等一线产品位，否则维护成本会失控。

  ---
  五、最关键的架构判断

  我认为你现在最需要的不是继续“加功能”，而是：

  做一次“架构收口”

  核心目标是这三个：

  1. 明确每个领域的唯一真实入口

  例如：
  - chat session 只能有一套存储
  - workspace 只能有一套持久化模型
  - knowledge 只能有一套路由实现

  2. 识别并消灭伪实现

  凡是这种情况都要重点清理：
  - 前端有按钮，后端没接口
  - 后端有接口，但只返回 success
  - UI 成功态与真实状态无关

  3. 把平台能力收敛成真实可用闭环

  与其 12 个模块都做 50%，不如先做 3 个模块闭环到 90%。
